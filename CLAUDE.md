# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`webscout` is a single-binary Rust CLI that searches the web and returns **verified** results. Three actors, strictly separated:

- **Generative LLM** (OpenRouter Gemma 4 by default, any OpenAI-compatible endpoint) *writes*: plans queries, extracts records, synthesizes prose. It never decides.
- **TypeSafe Jev** (`src/typesafe.rs`) *judges*: returns calibrated probabilities, never text. Used for triage, injection screening, grounding, and mission-parse checks.
- **Fetch backend** (`src/browser.rs`): `obscura` driven as a subprocess (default), or Jina's hosted reader when `JINA_API_KEY` is set. The key's presence is the whole switch for *fetching*. **Searching is separate**: `SearchLane`s run concurrently (`ddg` whenever obscura is available, `jina` whenever a key is present), so a Jina key no longer silently turns DuckDuckGo off. Pin one with `--search-engines <auto|ddg|jina>`.

Rust owns the loop, the thresholds, and the output. This separation is the design; don't let the LLM make accept/reject decisions or let Jev produce text.

## Commands

```bash
cargo build --release          # release profile is size/LTO tuned; binary in target/release/webscout
cargo test                     # ~100 unit tests, all in-module; no network
cargo test chunk               # run tests matching a name
cargo test -- --nocapture      # see test stdout
cargo clippy && cargo fmt      # no custom lint config
```

Running it needs credentials. Source the gitignored `env` file (real secrets, mode 600) or copy `.env.example`:

```bash
source env
webscout "who is the current CEO of Vodafone"                  # answer mission
webscout -f csv "at least 100 cooperative names with emails"   # harvest mission
webscout -vv --profile -f json "..." > out.json                # logs/summary to stderr, payload to stdout
env -u JINA_API_KEY webscout "..."                             # force obscura for one run
```

Required: `TYPESAFE_API_KEY`, `WEBSCOUT_LLM_API_KEY`. Flags always beat env vars. Nothing is ever hardcoded into the binary; keep it that way. Obscura runs need `obscura` and `obscura-worker` on PATH (or `--obscura-bin`).

There are no integration tests; anything touching the network is verified by running real queries. Exit code 0 means the run completed, including `outcome: empty`. Nonzero is reserved for breakage.

## Architecture

Everything lives in `src/` as one crate. `README.md` is long and accurate; it explains the *why* behind most design choices and measured numbers. Read it before changing thresholds, batching, or concurrency.

**Data flow — answer path** (`src/scout.rs`):

1. `parse_mission` — LLM classifies the request into `MissionKind::{Answer, Harvest}` plus a `simple` flag; Jev checks the parse is faithful (score < 0.5 → re-run, keep higher-scoring parse). Misclassifying here is the most expensive error. A harvest always carries an identity field: code prepends `name` when the classifier returned only attributes (`Mission::needs_identity_field`; a comparison whose fields are just its dimensions keys records by the first dimension value, producing page fragments; measured 2026-09-21 on q32). A concrete per-entity fact the request requires of every item (year, number, price, version — "founded after 2020", "fewer than 100 employees") becomes a **field** (`founded_year`, `employee_count`) as well as a constraint, so it is enriched and verified per entity instead of being trusted from the directory page that listed it (measured 2026-09-21, q10: fields=[name] only, and a 2013-founded company passed a "founded after 2020" filter because a startup-list page vouched for nothing specific).
2. `fetch_round` — plan queries (skipped for simple lookups), search, Jev-triage hits in batches, fetch the best pages. Talks to the web only.
3. `verify_round` — Jev injection-screens every chunk **before** the LLM sees it (failed screen = unsafe = dropped, never passed through), LLM extracts records, Jev grounds each value against its source passage. Below `--grounding-floor` the record is discarded and counted.
4. `steer` — Jev decides satisfied / exhausted (both checked as nouls, p ≥ 0.70); code maps `bottleneck` choice to an action; LLM writes new query strings only. Fixed rules (`--max-barren-rounds`, `--max-rounds`) are the fallback.
5. `assess` + `synthesize` — Jev checks the evidence answers the question (`answered` noul: ≥0.70 complete, ≥0.35 partial), then whether the written answer is stale/unsupported. A multi-part question is judged **per part**: `answer_parts` (the requested fields minus the subject) each get a noul in the same `assess` request, and `answered_across_parts` takes the minimum, so the search loop cannot stop — and the run cannot report complete — while a part is open; the planner is told which parts are missing (`STILL MISSING`). Measured 2026-09-23 (ElGamal, "when was it presented, and the link to the paper"): the holistic noul scored the date alone ≥ 0.7, the loop stopped after 1–2 rounds, 0 of 3 runs delivered the link; per-part, 3 of 3 did. A URL-shaped part, and the per-claim check, count an evidence item's own `source` as proof of its address — a paper's page never prints its own URL. The writer is told what the judge found: `CONFLICT_WRITER_NOTE` above `CONFLICT_FLOOR` (show the disagreement, e.g. presented 1984 vs published 1985, instead of picking one) and `missing_parts_writer_note` for open parts (say it was not found, never substitute a related item). `Empty` is reserved for evidence that supports nothing: an answer with at least one supported claim is at worst `Partial`. A **resolved negative counts as answered**: when the evidence is the authoritative place the fact would appear and the fact is absent there (the org's own contact page lists its emails and omits the one asked about), the answer is "no". Without that license, verification questions answered in the negative come back `empty` (measured 2026-09-21 on Decidim's info@ vs its published hola@).

**Data flow — harvest path** (two-phase loop in `run_harvest`):

Each round:
1. **Discover** (`fetch_round` + `verify_round` with `discovery_goal`): triage, screening, link-following and record extraction all use a stage-specific goal (`discovery_goal` / `extraction_goal`, one shared `listable_constraints` filter), except that a constraint naming a contact field (email/url/phone, `constraint_names_a_contact_field`) is dropped from it: no listing page demonstrates "publishes a contact email" in a snippet (measured 2026-09-21, q41: every hit 0.03-0.13 relevance, run ended empty; the field is enriched per entity and the post-enrich re-check upgrades the constraint); a constraint whose tokens are a superset of a field's own name-tokens (`constraint_mirrors_a_field`: "publishes pricing publicly" <-> `publishes_pricing_publicly`) is dropped too — a per-entity property of the entity's own page, while `founded_year` vs "founded after 2020" stays listable ("year" absent from the constraint). A third shape is decided by Jev, not by tokens: at harvest start one batched ask (`judge_listability`, one noul per constraint — *would a directory, register or member list state this per item?*) flags constraints into `Mission::unlistable_constraints`, and `listable_constraints` drops them exactly like the two heuristics (a failed ask keeps everything listable). One verdict is overridden in code: a constraint carrying an anchor token names the set itself (`constraint_names_the_set` — the register of NEOTEC 2024 grantees IS the list of things satisfying "awarded grants in the CDTI NEOTEC 2024 call"), and the per-item reading answers the wrong question for set-defining criteria — measured 2026-09-21, q81: the ask read both constraints unlistable, the goal collapsed to the bare entity type, triage scored the ministry's own resolution pages 0.08-0.13, and a generic companies directory supplied 146 records of which 1 was complete. Weak anchor tokens (bare years, common words) carry no set identity and never trigger the override. The ask's wording itself teaches the distinction: YES when the criterion names the population the list enumerates — where the entities operate, who uses or buys them (a country, city, sector, customer type), or the grant/award/certification the whole page is about, demonstrated by inclusion without per-row restatement; NO only for facts about each entity ALONE — quantitative or temporal measurements (headcount, revenue, founding year, dates of activity, prices) that no listing states and that select nothing about where the entities are listed (measured 2026-09-21, q101: "used by Spanish municipalities" read unlistable, discovery then accepted international voting platforms, grounding rejected them as wrong_entities, and steer exhausted at 8 records with the platform→municipality mapping empty). Both token rules miss whole shapes: "has more than one office in Spain" against the field `office_count_in_spain` shares no token superset ("count" is absent from the wording) and no member list states office counts per item — measured 2026-09-21, q84: every goal demanded it, triage scored the association's own member-list pages 0.07-0.14, thirteen rounds read those very pages while reporting `no_sources`, run `empty`. The parse prompt likewise forbids per-item factual qualifiers (office/employee counts, founding year, prices) in `topic` — q84's topic itself carried "with multiple offices in Spain" and poisoned every goal independently of the constraint list. A fourth mechanism fixes the topic itself: stage goals render through a **listing core** (`Mission::listing_core`), selected at the same harvest-start ask by one Jev `choice` over code-built clause prefixes of the topic (`listing_core_candidates` cuts at " that ", " which ", " who ", ", ", " and ", " with "; the full topic is always the last option, plus a temporal tail-trim — `trim_temporal_tail` strips a trailing year and its preposition, because "…ran online consultations in 2025" offers "…ran online consultations", a cut no clause marker separates; measured 2026-09-22, q62: the only marker cut was the bare entity type "municipalities", the judge took it, and the goal matched every population register on the web). Query building and steer keep the full topic — searches stay specific; only the accept-side goal names a list that can exist. The choice is taught that the qualifying activity ("using Decidim", "that ran online consultations") stays in a list's name while a bare entity type names every register of such things and identifies no list. Constraints render into goals as criteria ("where every item meets this criterion: …" in `discovery_goal`, "each meeting this criterion: …" in `extraction_goal`), never as a `that` clause: the graft flips an elliptical passive into an active verb — "Spanish companies, that awarded grants in the CDTI NEOTEC 2024 call" names the grantors — and triage rejected the BOE resolution, the ministry's announcement and the press listing of the 62 winners at 0.16-0.27 relevance in round 1 while BORME registry indexes later passed (measured 2026-09-22, q81 rerun; the per-record `constraint_evidence_question` already framed the same text as a criterion and read it correctly). The parse prompt likewise demands filters worded with the entity as understood subject ("was awarded grants in X", never a bare participle). Measured 2026-09-21, q63: the parse (with the new prompt) still folded "that ran a vote in 2025 and the organization responsible for managing that vote" into the topic, triage scored decidim.org/installations/ 0.19-0.23 for nine rounds, and the run returned 1 record. Extraction must use the same filtered goal, never the raw request: its prompt once carried `mission.query` plus every constraint, and the extractor — asked for entries that publish a contact email from pages that list names only — correctly returned zero records on every page read (measured 2026-09-21, q41 rerun with credits live: five pages read, `records_extracted=0` on each, run `empty` in two minutes; the per-record constraint judgment belongs to grounding and the post-enrich re-check). Extraction treats non-entity fields as optional, grounding checks entity presence + field association + constraint support in one batched request. Results are keyed by normalized entity (not by position in results). Discovery never stops early when entity count is below target. Enrichment visits records fewest-missing-fields first (`enrich_order`, grounding as tiebreak): a slot spent one field short of complete buys a counted record, a slot spent on a bare name buys nothing yet — measured 2026-09-21 (q102, 50 cooperatives × 8 fields), grounding-only ordering spread slots across 1203 entities and the run ended with 1 complete record in 133 minutes. A dry planner no longer ends the run while enrichment work remains (`count_enrichable` mirrors enrich_round's three eligibility rules): the loop switches to enrichment-only rounds — no planner call, no prefetch — and stops only when both discovery and enrichment are exhausted. Measured 2026-09-22 (q102 rerun): the planner ran dry at round 7 with 182 records, 0 complete and steer reporting `bottleneck=missing_fields` on every round; the old top-of-loop break stranded every record un-enriched at 16 of 182 emails. A round that fetched link-follow pages but issued no queries processes them instead of breaking.
2. **Follow links** (`follow_links`): pages with ≥ 2 entities have their outbound links Jev-scored with one noul per link; links above `follow_floor` are queued for the next `fetch_round`, bypassing search and triage.
3. **Enrich** (`enrich_round`): for each (entity, field) pair, code builds three query candidates (primary render, alternate render, bare `{entity} {field}`) and one batched Jev `choice` per pair (`select_enrich_queries`) picks which to search; a missing answer means the primary. `enrich_attempts` still skips a pair after two failures, but the phrasing is no longer a function of the attempt count. Then search + triage with `enrich_goal`, then — for regex-detectable fields — `candidates::find` → Jev `choice` + `none` + post-pick verification noul; no LLM call on this path. Non-regex fields use LLM extraction + Jev association. Per-field provenance is recorded for every enriched value. After a round's enrichment fills anything, `recheck_constraints_after_enrich` re-asks every mission constraint for the touched records with the enriched facts inlined in the question (`founded_year=2024` vs "founded after 2020"): `contradicts` excludes the record, `supports` upgrades a stale `not_addressed`, a weaker verdict never downgrades an existing support; a failed batch changes nothing.
4. **Near-collision merge** (`merge_near_collisions`): Jev `score` question with three levels (0 = different, 1 = ambiguous, 2 = same); `score` is a **level index**. A score ≥ 1.5 → merge, keep better-grounded values. Before pairing, records whose name is made only of the entity type's own words (`is_category_echo`: every name token, stopwords aside, appears in the entity type) are dropped, counted in `stats.category_echoes_dropped`, and excluded from the pair graph — a bare category word left in the store is a merge hub, because containment matches it against every name containing the word and transitive merges then swallow unrelated real entities through it; dropping it from the store while leaving it in the key list just hides the hub, since the union-find still bridges through it (measured 2026-09-21, OSS-CRM harvest: a dropped-but-still-paired `crm` key chained EspoCRM, CiviCRM, SuiteCRM and more into one group whose survivor, `krayin`, absorbed sixteen real projects). Collisions come from name overlap **or an identical published email** (`shared_email_pairs`, star-shaped so one brand's directory page costs n−1 questions, not n²/2); the email-pair question states the shared address and Jev decides one-operator-with-branches vs independent-organisations-sharing-a-mailbox — a federation directory that stamps its own email on every member must not collapse; floors differ by signal: name pairs merge at ≥ 1.5, email pairs at ≥ 1.0 ("ambiguous" plus an identical published address is a merge; measured: two listings of one operator at 1.44 stayed apart under the single floor). The merge runs before enrichment and, when enrichment filled something, again after it — a shared-email pair can only arm once enrichment attaches the operator's address, and a single-round run otherwise ends before any pass sees it (measured 2026-09-21, Barcelona coworking harvest: 9 CREC + 2 Aurea branches counted as 11 of "10 spaces" while the emails named 4 operators). The question carries the mission's entity type ("These are names of pricing plans…") — without it, decorated variants ("Basic $10" vs "Basic") score below the floor because a bare number is identity-carrying to a literal reader (measured on a Linear pricing harvest, 2026-09-21: 11 unmerged variants with the bare question, 1 with type context).
5. **Anchor-enumeration corroboration** (`anchor_corroborate`): when the mission is about one organisation ("the pricing page for Linear"), a page on that organisation's own site (`on_anchor_site` — domain-shaped anchor or host label equal to the anchor stem) that Jev reads as a *complete enumeration* (≥ `enum_completeness_floor`, 0.8) and that names ≥ `enum_min_yield` (3) entities becomes an authority: records contributed only by third-party pages are checked against it in one batched noul per page, and joint silence — complete enumeration, presence ≤ `enum_absence_ceiling` (0.2) — drops them, counted in `stats.anchor_unmentioned`. Measured 2026-09-21: Linear's pricing page (completeness 0.80, /changelog 0.04, /docs/billing-and-plans 0.14) dropped six SEO-invented "Plus"/"Standard"/"Pro Plan" rows. Partial listings never arm the gate, so directory-driven discovery is untouched; a failed ask never drops anything.
6. **Steer** (`steer`): same as answer path; `satisfied_by` counts only complete records (all fields non-empty). Steer is shown a per-round `history` (`RoundSnapshot`: found, complete, filled values — the last 8 rounds) and asks a `plateaued` noul in the same request. Under **auto rounds** (`Tunables::auto_rounds`, the default; `--max-rounds auto`, API/UI `"auto"`) a plateau verdict ≥ 0.7 ends the harvest from round `AUTO_MIN_ROUNDS` (4) on (`plateau_stop`) — but never while any enrichable pair is still untried (`count_untried`, carried in the snapshot) and never on a starved trajectory (a search batch lost to its deadline in the last `PLATEAU_CLEAN_WINDOW` rounds, counted by `Fetcher::lane_failures`): Jev judges the curve, code decides whether the curve measures the web or our own failure (measured 2026-09-24: without these, q81 stopped at round 4 with 62 companies and none classified after its enrichment batches were lost to the lane deadline, and q62 at round 4 with 454 found and 3 providers). The lane deadline itself scales with the batch (`lane_budget`: per-wave deadline × waves), like `Obscura::scrape`'s budget; the fixed 20 s was sized for a five-query round and lost whole 25- and 50-query enrichment batches. The plateau stop is deliberately not subject to `steer_stop_overridden`: that override exists because `satisfied` was blind to unfilled fields, while the plateau question sees fill progress directly — and on an open-ended list new half-filled records keep the override true forever (measured 2026-09-23, q62: 40 of 40 rounds on every rerun). Under auto the preset's `max_rounds` is only a safety net. A number the caller names turns auto off and is honoured exactly on both paths — no plateau stop, and the answer path's cap (`answer_round_ceiling`, `ANSWER_AUTO_ROUNDS` = 6 under auto) no longer clamps it.
7. **Research plan** (`plan_research`): one planner-LLM call per harvest run, framed as a research librarian, returns up to 8 scored sources plus a fan-out axis; Jev then scores each source by expected completeness. Round 1 = the query Jev selected, the raw request, then source queries in score order; seed URLs are fetched directly. The round-1 candidates are built in code (`build_query_candidates`) and one Jev `choice` (`select_query`) picks the primary — the judge selects, it does not generate, so a candidate cannot come out anchorless. That selected query is searched concurrently with `plan_research` (`futures::future::join`) and its hits are handed to round 1 rather than discarded. Later rounds fan out via `{anchor} {value} {source_type}`. Every query is anchored (`ensure_anchor` uses the stem — `Decidim`, not `Decidim.org`) and screened by the P4 Jev query gate (`query_gate_floor`, default 0.4; never drops below 2). Disable with `--no-plan`. Planner model slot is `--planner-model` / `WEBSCOUT_PLANNER_MODEL`.

Rounds are pipelined: round N+1's `fetch_round` runs while round N's `verify_round` is in flight, planning against knowledge one round stale by design. Rendering is serial (`--browsers` defaults to 1) because obscura's embedded V8 is not thread-safe across threads and concurrent jobs.

**Fetch fast path** (`src/browser.rs`): plain HTTP is tried first; the browser renders only pages that need JS. URLs whose path ends `.pdf` bypass the browser entirely — Chromium's viewer yields no text and obscura sometimes returns raw bytes that screen as junk (measured 2026-09-22, q81: 627,825 chars of PDF bytes, ten empty rounds) — fetched instead via `obscura fetch --dump original`, `%PDF`-magic-checked, and parsed with `pdf-extract`; on the CDTI resolution PDF this extracted all 62 beneficiaries at grounding 0.86-0.99 in one 83s run. The `--url` flag (repeatable) pins an answer mission's whole evidence base to named pages — still injection-screened — or seeds a harvest at depth 1. If a triaged page yields nothing over HTTP it is re-read with the browser before being written off. `extract_links` populates `page.links` from `<a href>` tags for `follow_links`. Search is a scrape of DuckDuckGo's HTML endpoint (`SEARCH_JS`) plus Jina's search endpoint, run as concurrent lanes with a per-lane deadline (`Tunables::search_lane_timeout`, 20s) so one stuck engine cannot cost the round another engine's results; empty results with a working network usually means the markup changed. Lane results are merged by `canonical_url` (tracking parameters dropped, `www.`/scheme/trailing slash folded), unioning `Hit.engines` so agreement between engines is visible downstream, and a repeated `title_key` drops a syndicated copy — but only a headline-length key (>= 4 words): a 2-3 word title is a programme name shared by distinct pages, and the short-title collision dropped the ministry's NEOTEC resolution page plus two other distinct pages as "syndicated copies" (232 drops in one run, measured 2026-09-21, q81). Successful, non-empty lane responses are cached on disk (`src/search_cache.rs`, `$XDG_CACHE_HOME/webscout/search`, 6h TTL; `--no-search-cache`, `--search-cache-ttl`, `WEBSCOUT_SEARCH_CACHE_TTL`). Measured 2026-09-18: only DuckDuckGo and Jina return usable results — Bing through obscura returns unrelated content behind `bing.com/ck/a?` redirects, and Brave, Mojeek, Startpage and Ecosia return interstitials or near-empty bodies. Adding a third engine is a `LaneEngine` variant.

**Candidates** (`src/candidates.rs`): regex-based extraction and normalization for email (including obfuscated forms), URL, and phone. `kind_for_field` maps field names to kinds; `find` returns deduplicated, normalized candidates; `appears_in` is the code-level gate before Jev questions.

**Jev client** (`src/typesafe.rs`): questions are built with `noul` / `choice` / `score` and batched into one request via `questions(...)`. Two limits measured 2026-09-18: `MAX_REQUEST_TOKENS = 65,536` (whole request), `MAX_STATE_TOKENS = 32,768` (state + longest question). `Jev::budget_chars()` uses an adaptive EMA of the observed chars-per-token ratio (alpha 0.3, clamped 2.0–3.5, initial seed 2.0 = measured worst case on email-dense data). Batch sizes are computed by serializing each item (`question_cost`, `state_cost`). An oversized batch gets a 4xx tagged by `is_oversized`; the caller halves it and retries (`split_on_oversize`) and the EMA resets to its 2.0 seed, so chunks are no longer dropped for being too big. Transient errors retry with jittered backoff; other 4xx verdicts never retry; a circuit breaker opens after 10 consecutive failures. **Jev reads literally** — "Ayuntamiento de Getafe" and "Getafe" are judged as different entities.

**LLM client** (`src/llm.rs`): strict `json_schema` decoding, with a retry that drops `response_format` and inlines the schema when a server rejects it. Reasoning is controlled at runtime by `ThinkingControl` (`--thinking-control`, and `--planner-thinking-control` for the planner transport): `auto` sends the OpenRouter `reasoning` parameter to openrouter.ai hosts and nothing elsewhere, `vllm` sends `chat_template_kwargs.enable_thinking`, `effort` sends `reasoning_effort`, `off` sends nothing. Pick the right one per server: a model that always reasons returns empty `content` with `finish_reason: "length"` and burns the whole budget. Measured on a self-hosted vLLM endpoint, one extraction call took 58.3s with reasoning and 1.4s with `vllm`. Chain of thought arrives as either `reasoning` or `reasoning_content`; both are read. Endpoints must be the full `/chat/completions` URL (e.g. `https://openrouter.ai/api/v1/chat/completions`); a wrong URL is rejected at startup with the corrected form suggested — do not pass a bare base URL.

**Config** (`src/config.rs`): every tunable threshold and default in one place, including `quick()` / `thorough()` presets and `chunk_cap(harvest)` (10 chunks/page for answers, 40 for harvests). `default_fetch_concurrency()` is the core count clamped 4..=16. Raising concurrency knobs beyond defaults measurably slows runs; the critical path is sequential stages, not parallelism.

**Output** (`src/output.rs`): five renderers behind `Format`. Results always go to stdout, logs and the run summary / `--profile` table always to stderr, so `-f json > out.json` stays a clean document at any verbosity. Stage timings are in the payload under `stats.stage_ms`. Harvest records include `provenance` (per-field `{source_url, grounding}`) and `constraint_support`. CSV adds `{field}_source_url` columns for fields enriched from a different page. Field names are chosen by the classifier; consumers must key off `mission.fields`.

**Invariants that must not be broken:**

- Jev decides; LLM writes. Never ask the LLM to make accept/reject decisions.
- A failed guard is never an open door: unverifiable chunks are withheld, unverifiable records are discarded and counted.
- `score` questions return a level index (0/1/2), not a probability. Do not treat it as a noul output.
- Both token-budget constants (`MAX_REQUEST_TOKENS`, `MAX_STATE_TOKENS`) bind independently; check both when sizing a batch.
- Harvest results are keyed by normalized entity (via `normalize_entity`, which also strips a single-slash `owner/repo` slug down to the repo so a GitHub listing and an article name for one project collide exactly), not by position in search results.
- Post-pick verification runs after every regex-path enrich accept; do not skip it.
- Discovery continues until `steer` says satisfied, exhausted or (under auto rounds) plateaued; never stop a harvest round early because entity count looks close to target. The stop is always a Jev verdict — the LLM never decides how long a run lasts.
- Every generated query carries an anchor stem — `ensure_anchor` appends the mission's anchor whenever the planner, steer or reviewer forgot; a query without its product name is a wasted search.
- Every generated query is Jev-gated through `gate_queries` before the round issues it; below `query_gate_floor` (default 0.4) queries are dropped, but never fewer than two of the best so a bad Jev batch can't starve a round.
- A round that returned hits but had every one rejected by triage is re-aimed via the planner LLM before it counts as barren; `Tunables::max_reaims` (default 2) caps the number of re-aims per run.
- Constraint checks are context-aware and five-way: per-record `c{i}_{j}` questions are `choice` with labels `supports` / `contradicts` / `not_addressed` / `ambiguous` / `mixed` (not a binary noul). The gloss from `parse_mission` is inlined, because bare-word constraints score ~0.22 on wording-variant pages (measured decidim.org/partners/ 2026-09-18). Measured with the five-way choice (2026-09-20): `supports` 0.98 for Pokecode on the same page; `not_addressed` 1.00 on a Decidim docs page that never mentions the entity; an announced intention against "executed participatory budgeting at least once" returns `not_addressed` 0.65 / `contradicts` 0.33 / `supports` ≈ 0.00 — it refuses to read an intention as an execution. Consequence per verdict: `contradicts` excludes the record outright (`stats.excluded_contradicted`); a page-level rescue (`p{j}` noul ≥ 0.70) **never** overrides a contradiction. `not_addressed` / `ambiguous` / `mixed` keep the record but it is not complete and not counted toward the target (`stats.constraints_unverified`); these three are eligible for the existing page-level rescue. `supports` above `constraint_floor` counts. A failed Jev call reads as `not_addressed`, never `supports`. Never revert to bare-word checks or binary nouls for constraints.
- Entity binding is a four-way `choice` (`same` / `related` / `different` / `unresolved`) asked on the **enrichment path only** — after a candidate value is chosen, to confirm the page's organisation is the target entity. Accept only when the argmax label is `same`; `related` and `different` reject regardless of the margin (`stats.wrong_entity_rejected`); `unresolved` falls back to a stricter acceptance floor. Never use a probability threshold: measured (2026-09-20), Terrassa vs the insurer Egarsat returned `related` 0.53 / `different` 0.36 — a margin any confidence gate would have let through, while correct attributions (Bilbao, Sant Adrià de Besòs) returned `same` 1.00. **Do not ask entity binding during discovery.** On a listing page that names forty municipalities the question is ill-posed — the passage describes the list, not one organisation — and adding it collapsed a harvest from ~38 entities to 4, with rounds logging pages yielding records but zero gained. A `related` record is kept in the output but is never complete and never counts toward the target.
- Oversized Jev batches split and retry (`split_on_oversize`, up to 4 halvings) rather than being dropped; on `max_tokens_exceeded` the chars-per-token EMA resets to the 2.0 seed. Only an unsplittable single-item batch that is still oversized falls to the ungrounded fallback.
- Anchor-domain pages are explored by `follow_links` regardless of entity yield: seeds (depth 1) always, anchor-domain pages (depth 2) always, deeper pages fall back to the ≥ 2-entities yield rule. Do not gate anchor-domain navigation on yield.
- Language-variant URLs are deduped by `lang_dedup_key` (host + path-after-`/xx/`-prefix) before Jev scores them; only the first variant of each page is followed. Do not send translation copies to Jev — they consume quota and add nothing.
- Search lanes are merged by `canonical_url` (scheme, `www.`, trailing slash and tracking parameters folded); engine agreement is a tiebreak applied *after* Jev's keep/drop decision and only reorders results — a result Jev wants to drop cannot be rescued by engine count.
- Every claim in an answer is Jev-checked against the evidence, one noul per claim in a single request (`split_claims` splits in code, `verify_claims` asks). A claim below `claim_floor` (default 0.5) is marked ` [unsupported]` in the answer text, counted in `stats.unsupported_claims`, listed in a note, and downgrades `Outcome::Complete` to `Partial` — never returned silently. Marked, not deleted: removing a sentence breaks the citations after it. Measured 2026-09-19: the whole-answer `unsupported` noul returned 0.98 on a four-sentence answer with two invented sentences, while the per-claim nouls returned 0.98/0.98/0.03/0.03 — detection was never the gap, localisation and consequence were. A failed claim check is `None`, never "supported".
- Query wording is selected by Jev from code-built candidates (`build_query_candidates`, `select_query`, `select_enrich_queries`), never generated by the LLM; a candidate cannot come out anchorless because no unconstrained string is ever offered to Jev.
- Every stage that could resolve "latest", "next" or "current" is told today's date. `Scout.today` is read from the clock **once** (`clock::today_utc`, `src/clock.rs`, no date crate) and threaded into the Jev state of `triage_batch`, `screen_chunks`, `screen_passages`, `assess` and the final answer verification, and into the prompts of `parse_mission`, `reparse_mission`, `plan_research` and `synthesize`. Measured cause: with no date and no evidence, `google/gemma-4-31b-it` answers "two seasons of The White Lotus are available, and the third is expected in 2025" — its training cutoff speaking. Never call the clock inside a loop and never drop the date from one of these states.
- The finished answer is checked for staleness (`stale` noul) alongside `unsupported`. Above `STALE_FLOOR` (0.5) `synthesize` runs **once** more with `stale_retry_instruction`, the better draft wins (`prefer_retry_draft`: lower `stale`, then lower `unsupported`), and a still-stale draft downgrades `Complete` to `Partial` with a note rather than being suppressed.
- `Mission.time_sensitive` buys the per-chunk `cur{slot}` currency noul on the answer path only. `currency` multiplies `supports` in `passage_rank`, so a non-time-sensitive run sorts exactly as before; only below `Tunables::currency_floor` (0.25) is a passage dropped.

## Conventions worth keeping

- Comments in this codebase explain measured reasons ("segfaults with >1 browser thread", "2.0 chars/token measured"). When you change a limit, update the comment with the new evidence.
- A failed guard is never an open door: unverifiable chunks are withheld, unverifiable records are discarded and counted in stats. Quarantined pages are reported by URL, not silently dropped.
- No time limits anywhere; runs stop on target reached, barren rounds, exhausted angles, a plateau (auto rounds only), or the round ceiling (reported as `truncated`).
- The parent directory holds an older Go implementation (`../cmd`, `../internal`) and a Python `scout/` package. They are separate; this crate does not depend on them.
